## The model

Every check is one question, answered in one place (`can(who, action, resource)` in `server/access.js`): can this person (or Innowa acting for them) do this action on this thing? A role is a fixed bundle of actions, held at a level of the tree, and it reaches everything below.

Two trees that never mix: the **platform** (BuilderPluss staff: code, servers, the platform knowledge layer) and **client organizations** (tenants: their people, workspaces, projects). A platform role never gives standing access to a client's data.

```
Platform                     Organization (a firm) → Workspace → Project → model, files, runs, notes, chats
                                                                  └ guests from other organizations, per project
```

### Roles

- **Platform:** Platform Owner, Ops, Developer, Platform FDE (knowledge engineer), Support (no data; break-glass only); later Customer Success, Billing, Auditor.
- **Organization:** Owner, Admin, Member, FDE (from BuilderPluss, invited by the client, with an end date: the org's knowledge layer and settings, not members or billing, not project data unless added to a project), later Billing.
- **Workspace:** Manager, Contributor, Viewer.
- **Project:** Lead, Editor, Reviewer (views, comments, answers decisions: client sign-off), Viewer. AEC labels (architect, consultant, client, contractor) are names on these, not more roles.
- **Agents act as a person, never as themselves:** Innowa in a chat has that person's role on that project; a pipeline's agents have the starter's role narrowed to the step's tools; background agents run as a narrow service identity of the organization. Every action is recorded as who, as whom, by which agent.

### Actions

`org.manage, org.billing, org.members, workspace.manage, workspace.create_project, project.view, project.edit, project.share, project.delete, project.export, model.edit, files.add, files.download, run.start, run.decide, run.cancel, chat.use, knowledge.propose, knowledge.approve`, plus platform actions (`platform.deploy, platform.support_access, platform.knowledge`).

## The owner's decisions (8 Nov 2026)

- Staging is a **second site on the same server** (staging.studio.builderpluss.com).
- Break-glass support access: the **Platform Owner may approve it in an emergency, and the client is told afterwards**; otherwise the client approves. Read only, time-limited, logged, shown to the client.
- Platform roles now: **Balaji: Platform Owner and Ops. Bikal: Developer and Platform FDE.**
- Claude keys stay in each person's Helper, never on the server (R22's plan); usage is shown per organization.

Defaults taken where the owner has not decided (to confirm): workspaces built in from the start, with one default workspace hidden until a firm makes a second; a new project is open to its workspace's members, and clients and other firms are invited per project; an organization's own lessons, Objects and patterns stay private to it; an FDE's knowledge changes are proposals the client approves (direct changes an option the client can switch on); anyone with an email can be a project guest.

## Build plan (each step its own pull request, merged on the owner's word)

1. **Tenancy core and the platform plane.** Tables: organizations, workspaces, memberships (person, level, role, until), project roles; the role → action table; `can()` reading them, with today's member list replaced. Migration: the BuilderPluss organization with a default workspace; every project, chat and run moves in; Balaji its Owner, Bikal a Member; platform roles as above. Every page request, notice, file, Helper route and member's Innowa tool goes through `can()` (as `server/access.js` does now). Pages: Organization (people, roles, workspaces), a project's People card (roles instead of "Shared with"), a workspace switcher. Support access: request, approve (client, or the Platform Owner in an emergency), read-only window, the client's notice.
2. **Project roles and guests.** Lead, Editor, Reviewer, Viewer on a project; inviting someone from another firm (or with no firm) to one project; Reviewers answer pipeline decisions; the org FDE role (with an end date) on the same mechanism.
3. **Claude per organization.** Runs go to the Helper of the person they are for (as now), under the organization's policy; usage and cost per organization, workspace and person, from the run costs.
4. **Knowledge layers.** The platform layer (aec-studio-content, run by Platform FDEs, gated by replayed briefs) under each organization's own layer (its lessons, Library Objects, patterns, pipelines and agents), proposed and approved inside the organization; guests see the platform layer and their project only.
5. **Staging and hardening.** staging.studio.builderpluss.com on the same server (its own port, database, data folder and branch; the deploy action gets a target); audit view per organization ("what our FDE did", support access, role changes); access review; two-factor sign-in for owners, admins and platform roles; Google/Microsoft sign-in later; export and delete an organization's data.
